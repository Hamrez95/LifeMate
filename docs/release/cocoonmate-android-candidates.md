# CocoonMate Android candidates

CocoonMate uses two complementary GitHub Actions workflows:

- `cocoon-module-host`: PR validation for the reusable module, thin host, shared runtime/client contracts and a clean Android debug build.
- `cocoon-android-candidate`: traceable Android candidate generation from `main` or a manual GitHub/mobile-browser trigger.

## Candidate identity

The standalone application is generated with the stable Android package ID `com.mylifemate.cocoonmate` and display name `CocoonMate`. This must remain distinct from WellMate and CareMate so internal testers can install the applications side by side.

`cocoon-android-candidate` names every uploaded bundle from environment, build mode, semantic version, GitHub run number and source SHA. The uploaded directory contains:

- the exact APK tested/generated by the workflow;
- a SHA-256 checksum;
- `provenance.json` with commit SHA, workflow/run identity, version/build number, environment, package ID and latest canonical migration filename.

Do not rebuild a different binary after recording QA evidence. QA should reference the candidate artifact/run and checksum.

## Manual trigger

From GitHub Actions, choose **cocoon-android-candidate** and run the workflow. This is intentionally usable from the GitHub mobile browser/application.

Inputs:

- `environment=internal`, `build_mode=debug`: normal internal test candidate and default manual choice.
- `environment=internal`, `build_mode=release`: signed internal release-shaped candidate.
- `environment=production`, `build_mode=release`: production candidate.

A production debug artifact is rejected before build. This prevents an artifact labelled production from using the debug build path.

## Release signing

Release mode requires all four repository Actions secrets below. Their values must never be committed, printed, embedded in provenance, or uploaded as artifacts:

- `COCOON_ANDROID_KEYSTORE_BASE64`
- `COCOON_ANDROID_KEYSTORE_PASSWORD`
- `COCOON_ANDROID_KEY_ALIAS`
- `COCOON_ANDROID_KEY_PASSWORD`

The workflow materializes the keystore only inside the ephemeral runner workspace, configures the generated Android project, builds the APK and uploads only the candidate directory. Missing signing material fails closed.

Rotating a key/credential is an operator action in repository secrets; no source-code change should contain the secret value.

## Environment contract

The selected environment is passed to the Flutter build as `LIFEMATE_BUILD_ENV` and recorded in provenance. Authoritative API/runtime origins remain controlled by the shared LifeMate runtime strategy implemented by #784/#753; this workflow must not introduce Cocoon-specific provider URLs or credentials.

Sensitive/paid product state still fails closed in the application when authoritative runtime/Commerce/bootstrap services are unavailable. An artifact label or build mode is never an entitlement or health authorization signal.

## Versioning

The semantic version comes from `cocoonmate/pubspec.yaml`. The candidate build number is the GitHub workflow run number, making it deterministic and monotonic within this workflow. Provenance always records the full source commit SHA.

## Regression boundary

This workflow does not modify WellMate or CareMate packaging/signing. Shared Cocoon PR validation remains in `cocoon-module-host`; later changes that alter `packages/lifemate_client` or other shared packages must continue running their existing repository-wide regression checks in addition to Cocoon-owned validation.
