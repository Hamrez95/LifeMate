# Release Flow

`tools/lifemate.ps1` is the Windows PowerShell 7 console for the three independent Flutter Android hosts currently in this repository: WellMate, CareMate, and CocoonMate. Its readable app inventory is [`tools/lifemate.apps.json`](../tools/lifemate.apps.json).

## Everyday commands

```powershell
pwsh .\tools\lifemate.ps1
pwsh .\tools\lifemate.ps1 -List
pwsh .\tools\lifemate.ps1 -Health
pwsh .\tools\lifemate.ps1 -App wellmate -Build Debug
pwsh .\tools\lifemate.ps1 -App caremate -Build Release -Format AAB
pwsh .\tools\lifemate.ps1 -App cocoonmate -Run -Target Chrome
pwsh .\tools\lifemate.ps1 -App wellmate -Run -Target Chrome
pwsh .\tools\lifemate.ps1 -Logs
pwsh .\tools\lifemate.ps1 -Logs -LogView Errors -LogLines 150
pwsh .\tools\lifemate.ps1 -All -Build Debug
pwsh .\tools\lifemate.ps1 -App wellmate -Install
pwsh .\tools\lifemate.ps1 -App wellmate -DispatchWorkflow -Bump patch
```

The interactive menu provides the same operations. It is intentionally quiet and uncoloured with `-NonInteractive`, which makes it suitable for automation.

## Version and release policy

Remote Git tags are the final version authority. Every mobile app uses `<app>-v<version>` tags. Before a local release, the console fetches `origin`, checks the working tree is clean and the current branch is not behind its upstream, and checks the requested tag with `git ls-remote`. It never derives a release version solely from `pubspec.yaml`.

For every product, the build number is `git rev-list --count HEAD`, matching the reusable GitHub release workflow. The console requires typing `RELEASE` before it edits a version, tests/builds, commits, and creates a local tag; it requires `PUSH` separately before either commit or tag is pushed.

The product release workflows are `workflow_dispatch` workflows. They calculate and publish their own immutable tag and GitHub Release; use `-DispatchWorkflow` when that protected CI route is desired. The console does not alter those workflows or inject secrets.

CocoonMate now uses the same `GitCommitCount` build-number rule, `<app>-v<version>` tag contract, APK/AAB release outputs, release dispatch inputs, GitHub Release publication, and per-app release concurrency as WellMate and CareMate. Its older candidate workflow remains available for candidate-only testing. Its Android host is generated by the existing preparation script: for a local Android action, the console requires Git Bash and the three explicitly supplied public runtime variables (`SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and `LIFEMATE_API_BASE_URL`). Chrome needs none of these and can be run directly with `-Target Chrome`.

## Local builds versus CI

Local builds are for fast diagnostics. Their APK/AAB copies are placed under `artifacts/<app>/<version>/`, with a timestamped filename and a JSONL record in `artifacts/_reports/build-history.jsonl`. Local release signing is not configured by this tool; signing secrets remain GitHub Secrets for the CI workflows.

GitHub Actions is the trusted publishing path: it has protected signing material, creates its own immutable artifact/GitHub Release where the existing workflow supports it, and owns any workflow-specific environment validation. The Health screen shows the last configured workflow run when `gh` is installed and authenticated (`gh auth login`).

## Local diagnostic logs

Every command run through the console writes a redacted local operational log to `artifacts/_reports/lifemate-console.log`. Use menu item **Recent logs**, or `-Logs`; add `-LogView Errors` to show only failures. When a Flutter app is running in Chrome through the console, the same view also reads its live Chrome diagnostics and summarizes only safe API status/error-code/correlation metadata. Error lines are red, warnings yellow, and successful operations green in an interactive terminal. Logs never intentionally retain access tokens, API keys, passwords, request bodies, health notes, medication names, attachments, or other health data.

The Flutter API client records only privacy-safe failure metadata in the debug console: HTTP status, stable error code, and server correlation ID when available. The treatment-create screen also writes these three fields in debug mode. Use the correlation ID with the protected server log system when an API response needs deeper investigation; do not copy patient data, Authorization headers, or request payloads into an issue.

If a CI release fails before a tag is created, fix the failure and dispatch it again. If a tag already exists, do not reuse it: inspect the failed run and GitHub Release, then choose the next version. The console stops before creating a duplicate remote tag and suggests the next patch version.

## Standard release checklist

1. Start with `pwsh .\tools\lifemate.ps1 -Health` and resolve a dirty tree, a branch behind `origin`, or missing SDK/tool warnings.
2. Run a local Debug build or Chrome run for fast feedback. This does not publish anything.
3. For a signed distributable, prefer `-DispatchWorkflow`; GitHub Actions owns signing material, release artifacts, immutable tag creation, and GitHub Release publication.
4. Use `-Release` only when the local release path is intentionally required. Read its displayed summary, type `RELEASE`, inspect the build, then type `PUSH` only when the commit and tag are correct.
5. After CI completes, inspect its workflow run, GitHub Release, APK/AAB assets, checksums, and target tag before distribution.

Never reuse a tag after a failed or partially published release. Find the failure first; if a tag was created, publish a new patch version after the correction.

## Add a new app

Use this checklist when adding a new independent mobile app. Do not copy an app name or package id by assumption.

1. Create the real app host, its `pubspec.yaml`, Android package identity, tests, and documented runtime configuration first.
2. Add a matching entry under `apps` in `tools/lifemate.apps.json`: real `path`, `technology`, `versionFile`, `formats`, `tagPrefix`, `buildNumberStrategy` (`GitCommitCount`), and release `workflow`.
3. Add a `release-<app>.yml` caller based on `release-wellmate.yml`. It must call `reusable-mobile-product-release.yml`, supply `<app>-v` as `tag_prefix`, use the app's exact Android `package_id`, and map only that app's signing secrets.
4. Keep the shared workflow as the single release implementation. New release callers must use its per-app `release-<app>` concurrency; do not duplicate signing, artifact naming, tag, or GitHub Release logic.
5. Add the app and its relevant shared packages to the appropriate CI path filters. Preserve existing candidate workflows when they represent a different verification purpose.
6. Add any special generated-host preparation as an explicit, reviewed workflow input/step. Do not generate or commit signing material, runtime secrets, or guessed service endpoints.
7. Run `-List`, `-Health`, an unsigned local Debug build, and the release workflow in a safe test channel before using a production release.

The tool also discovers unconfigured Flutter hosts (outside `sources/`) and labels them as needing configuration rather than guessing build or release behaviour.

`-Clean` shows every generated `build` directory and requires `CLEAN`; it preserves source and managed artifacts. No tool, SDK, package, device, tag, or workflow is installed, changed, or deleted automatically.
